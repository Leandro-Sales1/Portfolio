# CLAUDE.md

Este arquivo fornece orientações ao Claude Code (claude.ai/code) ao trabalhar com o código neste repositório.

## Comandos

```bash
npm run dev      # vite — servidor de desenvolvimento
npm run build    # vite build — saída em dist/
npm run lint     # eslint . --ext js,jsx --report-unused-disable-directives --max-warnings 0
npm run preview  # vite preview — serve o build de produção
```

- Gerenciador: **npm** (só existe `package-lock.json`). Node **22.x** via `engines` no `package.json`, sem `.nvmrc`.
- **Não existem scripts `test`, `format` ou `deploy`, nem runner ou arquivos de teste.** Não invente um comando de teste.
- O `lint` usa `--max-warnings 0`: qualquer warning quebra o comando, inclusive a regra `warn` de `react-refresh/only-export-components`.
- O `lint` fixa `--ext js,jsx`, então ignora silenciosamente outras extensões se um `.ts`/`.tsx` for adicionado depois.
- O `.eslintrc.cjs` usa `env: { browser: true, es2020: true, node: true }`. O `node: true` é necessário para os arquivos de config da raiz (`postcss.config.js` usa `process`); sem ele o `lint` falha inteiro com `'process' is not defined`. O `ignorePatterns` inclui `flowforge-saas-1` — ver a nota sobre o template no fim.
- Não há `.github/workflows/` nem `vercel.json` no repositório. O deploy é a integração git da Vercel configurada no painel (build `npm run build`, saída `dist`), fora do repositório.

## Arquitetura

**Entrada e composição.** `index.html` → `src/main.jsx` (`React.StrictMode`) → `src/App.jsx`. O `App.jsx` é a página única e o **único** dono do estado de idioma: guarda `isEn` e repassa o objeto de locale inteiro por props. Não há router (`react-router` não é dependência), não há context, não há store.

`App.jsx` compõe, em coluna vertical: `Hero` → `About` → `TechsGrid` → `Projects` → `Contact` → `Footer`, todos em `src/components/sections/`.

- `src/components/ui/` — 5 primitivas: `Container`, `Section`, `Button`, `Badge`, `LangToggle`. **Pare aqui.** Não crie `Card`, `Heading`, `Text` ou `Stack`; os cards são estilizados inline com o padrão de borda de fio (ver `DESIGN.md`).
- `src/data/` — `techs.js` (os **20** ícones `{name, Icon, color}`, alinhados ao CV em 2026-09-23; o grid fecha 4 linhas exatas de 5 em `lg`), `socials.js` (LinkedIn/GitHub/WhatsApp) e `nav.js` (âncoras das seções). São a fonte única: a nav do Hero e a do Footer leem de `NAV`, então não têm como divergir. **Abaixo de `md` o Hero não tem nav nenhuma**: a linha de pílulas roláveis que existia ali foi removida a pedido do dono em 2026-09-23 ("no mobile, retire a barra de navegação superior"), e no telefone os anchors vivem só no rodapé. O `LangToggle` fica no header em qualquer largura.
- `src/utils/pointerGlow.js` — **não é hook e não observa nada**: são dois handlers (`setPointerGlow` / `clearPointerGlow`) que escrevem `--mx`/`--my`/`--rx`/`--ry`/`--lift` direto no DOM. Escrito assim de propósito, para não re-renderizar o React a cada `pointermove`.
- `src/utils/freeSpot.js` — duas buscas puras (sem DOM, sem three, sem React), que são as duas perguntas do posicionamento do fundo 3D do Hero: **`findFreeSpot(width, height, rects, {columns, rows, margin})`** devolve o **maior círculo livre** que não cruza nenhum retângulo (é o plano B e a régua de tamanho), e **`findSpotNearest(width, height, rects, {margin, minRadius, sizeFloor})`** devolve o ponto **mais perto do centro da tela** que ainda tenha `sizeFloor` (fração) do maior raio e `minRadius` (absoluto, em px) de piso — devolve `null` se nem o maior círculo alcança o piso, e aí quem chama fica com o maior vão. A régua do piso é medida **dentro** do `findSpotNearest`, com a mesma `margin` da busca: um piso absoluto vindo de fora comparava dois números medidos com réguas diferentes e nunca era alcançável. As duas são puras de propósito, para poderem ser exercitadas em Node com retângulos sintéticos. As duas devolvem `{x, y, radius, obstacle}`: `obstacle` é a distância ao retângulo mais próximo **sozinha** (na mesma régua, sem as bordas do container), e existe porque quem consome depois não é só o vão — é o teto da nuvem, que precisa saber onde o obstáculo está.
- `src/utils/screenBudget.js` — a "função que lê o tamanho da tela" do fundo 3D, também pura: `viewportBudget(width, height, {hasPointer, devicePixelRatio})` devolve o que a tela dá (folga, teto, piso, `pixelRatio`, recuo em `z`, `centerSizeFloor`); `envelopeWorldRadius({usedPx, fPx, distance, offsetPx})` inverte a silhueta; e `radiusWithinGap({ceilingPx, obstaclePx, fPx, distance, offsetPx, cloudRatio})` é o **teto da nuvem** — devolve o teto intacto onde a nuvem cabe (praticamente toda tela) e o maior raio que ainda não a deixa cruzar o obstáculo onde não cabe. Recebe dimensões **já medidas** e nenhum retorno pode virar `className` (é o teste que impede a função de virar um `isMobile` de volta). **Não devolve nome de faixa** (`'phone'`, `'desktop'`) — enum é convite a `if (tier === …)`.
- `src/api/instance.js` — inalterado.

**O idioma é feito à mão — não existe biblioteca de i18n.** `src/locales/pt.json` e `src/locales/en.json` (38 chaves cada) são importados direto no `App.jsx`, e `const text = isEn ? en : pt` desce para todo componente como a prop `text`. Os componentes consomem o **objeto inteiro** (`{text.aboutMe}`, `{text.linkCV}`), não uma função `t()`. O switch é o `src/components/ui/LangToggle.jsx` (dois `<button aria-pressed>`), **não** mais um checkbox estilizado por CSS.

- **Português é o padrão**, mas a escolha **é persistida** em `localStorage` (`portfolio:lang`) desde o redesign; o `useState` inicial lê essa chave, então um reload mantém o idioma.
- Um `useEffect` no `App.jsx` sincroniza `document.documentElement.lang` (`en` / `pt-BR`) com o estado.

O modo de falha é uma seção silenciosamente em branco. Ao adicionar chave, compare os dois arquivos (`Object.keys` de cada um).

Exceções deliberadas: nomes próprios (Leandro Sales, LinkedIn, GitHub, WhatsApp, nomes das techs) e os **índices mono das seções** (`01`–`04`, neutros de idioma). Os **labels do painel de calibração saíram desta lista** em 2026-09-23 (ver abaixo).
- **As meta tags do `index.html` não acompanham o toggle de idioma.** `<title>`, `description`, `og:*` e `twitter:*` estão fixas em PT (o `<html>` é `lang="pt-br"` e o PT é o padrão); o `App.jsx` só sincroniza `document.documentElement.lang`. Trocar o texto dessas tags é editar o `index.html` à mão nos dois lugares (title+og+twitter), não o locale.

**O texto dos projetos é uma segunda camada de localização, e vem da API.** Cada objeto traz `descricao` (PT) e `descricaoEn` (EN), e o `Projects.jsx` resolve antes de descer a prop (`isEn ? card.descricaoEn || card.descricao : card.descricao`) — o `||` evita card em branco quando a versão EN não foi preenchida.

**Os cards de projeto vêm de uma API remota, não do repositório.** `src/api/instance.js` exporta um axios com `baseURL` **hardcoded** (`https://json-server-portfolio.vercel.app`, sem env var e sem fallback). Único consumidor: `Projects.jsx`, com `instance.get('/cards', { signal })` dentro de um `useEffect` com `AbortController`. Campos consumidos: `imagem`, `titulo`, `descricao`, `descricaoEn`, `link`, `gitHub`.

- **A API não tem campo `id`** (verificado em 2026-09-22: 7 cards, chaves `imagem, titulo, descricao, link, descricaoEn`, e `gitHub` presente em só **3 dos 7**). Então `key={card.titulo}` é a única opção — **quebra se dois projetos tiverem o mesmo título**.
- A falha da API virou três estados (`loading` / `ok` / `error`) com skeleton, mensagem traduzida e botão de retry. O antigo `alert()` bloqueante e fixo em português foi removido — não o reintroduza.

> Para mudar o conteúdo dos projetos, edite o JSON server externo — **não este repositório**. E os valores de `imagem` são caminhos absolutos `/imagens/...` resolvidos contra `public/`.

**Fundo 3D.** `src/components/backGround/ThreeCanvas.jsx` — `three` puro (`ShaderMaterial` com shaders GLSL de ruído simplex, `IcosahedronGeometry`, `AdditiveBlending` + 3 órbitas `EllipseCurve`). Não usa `@react-three/fiber`.

- **As órbitas são `THREE.Line` + `LineBasicMaterial` e NUNCA são ocluídas.** São 1px de espessura (o WebGL ignora `linewidth`, então não há como engrossá-las) e entram no `lineGroup` **depois** das `particles`, que são `depthWrite: false` — ou seja, nenhuma nuvem passa na frente delas. Logo a visibilidade delas é **puramente contraste**, e era aí que estava o defeito: `0x27272a` @0,5 desenhava rgb(22,22,27) sobre o `#050505` do fundo, 17 níveis de diferença, invisível na prática. Hoje é `0x52525b` (zinc-600) @0,75 ≈ rgb(63,63,69), 58 níveis acima do fundo (a nuvem, `#d4d4d8`, está em 212). **Não "conserte" isso mexendo no tamanho ou na posição: o problema era cor.** Os raios dos três anéis são frações de `ORBIT_RADIUS` multiplicadas por `ORBIT_ENVELOPE_RATIO`, que hoje vale **1,1** — o anel de fora desenha **110%** do círculo reservado. Em 100% ele ERA o círculo por construção (a escala do grupo é `envelopeWorldRadius(usedPx) / ORBIT_RADIUS`), e era esse o limite que o dono mandou furar em 2026-09-23: *"as órbitas também estão nesse limite, tipo a esfera ocupa 100% do espaço, porém gostaria que as órbitas ficassem em 110%, por exemplo, pois tem espaço na tela para isso"*. A bola fica onde ele aprovou e só os anéis andam — e **a alavanca das órbitas não é um número próprio, é o `cloudRatio`**: `ORBIT_ENVELOPE_RATIO` é **derivado** dele (`= CLOUD_MAX_RATIO`), porque acima dele os anéis saem da garantia do `radiusWithinGap` e podem encostar no texto no extremo do slider. A ordem do array é a velocidade de giro (`rotation.z += 0,003 * (índice + 1)` no RAF): por isso ficam em ordem crescente, para o de fora continuar sendo o mais rápido.

- **Cada órbita tem uma BOLINHA que anda pela linha, e a velocidade dela é a "Taxa de Clock"** — pedido do dono em 2026-09-23: *"adicione também, 1 esfera a cada órbita que «ande» pela linha da órbita, e coloque a velocidade dela de acordo com a taxa de clock"*. São três `THREE.Mesh` + `SphereGeometry(BEAD_RADIUS = 0,05, 12, 12)` com `MeshBasicMaterial` em **`0x71717a` (zinc-500)** — um degrau acima do fio (`0x52525b` @0,75 ≈ rgb(63,63,69); a bolinha desenha rgb(113,113,122)) e muito abaixo da nuvem (212). A cor **não** vem do `color` do painel: as cores do "Energia" são da nuvem. A bolinha é **filha do `THREE.Line`** do anel (herda a inclinação; a elipse é o círculo de raio `radius` no plano LOCAL, então avançar o ângulo local é andar pela linha), o `0,05` é raio **LOCAL** (a escala do grupo o multiplica: ~5,8px de diâmetro em 2529×1344) e ela entra no passo **opaco**, então a nuvem passa na frente dela quando está à frente — as órbitas continuam sem oclusão. O ângulo é **função pura** de `timeRef` (`timeRef · BEAD_ANGLE_RATE (0,2) · (índice+1) + fase de 120°`), e é isso que a amarra ao clock: o relógio anda `0,01 + 0,05 · clock` **por quadro**, a mesma unidade do `uTime`. Três consequências que já confundiram uma vez: (a) **o giro do anel a carrega também**, então a velocidade que se lê é a SOMA das parcelas (iguais na taxa padrão) — a 60 fps uma volta completa leva ~5,8s / ~8,7s / ~17,5s (de fora, do meio, de dentro) na taxa padrão, ~3,5s / ~5,2s / ~10,5s no topo do slider (0,5) e ~7,0s / ~10,5s / ~21s no zero, onde o termo constante do relógio mantém tudo andando; (b) nada acumula, então travar o FPS não muda o passo — mas o relógio é POR QUADRO, então numa tela de 120Hz tudo anda 2× mais rápido que a 60Hz, e as bolinhas andam o dobro; (c) **esta é a única alavanca de velocidade das bolinhas e ela não é de layout**: `BEAD_ANGLE_RATE` só muda o passo, não o tamanho nem a posição da esfera. **E a casca da bolinha passa da envolvente do `cloudRatio`** em 0,76% (`6,6 + 0,05·escala` de mundo, ~+3,2px em tela em 2529×1344, contra um obstáculo a 401,8px e `marginPx` de 56px): é o **único** elemento da cena fora da garantia do `radiusWithinGap`, e quem absorve é a folga — se a folga cair para ~4px, essa conta precisa entrar na guarda, não a do anel.

O contrato com o painel de calibração é **5 props que viram uniforms**: `distortion` → `uDistortion`, `detail` → `uSize` (`detail * 2.0`), `speed` → `speedRef` (lido dentro do RAF), `opacity` → `uOpacity`, `color` → `uColor`. Todas mudam **ao vivo após o mount**.

- O `useEffect` de init tem **deps vazias de propósito** e fecha sobre as props (daí o `eslint-disable react-hooks/exhaustive-deps` no topo). **Não adicione as props às deps** — o canvas seria destruído e recriado a cada arrasto de slider.
- O estado do painel vive no `Hero` como **um objeto** `params`; `HeroCalibration` é controlado (`params` / `onChange`).
- **`adjustLayout` NÃO usa mais números por breakpoint.** Duas tentativas anteriores usaram constantes (`y = -2.9` + escala `0.72` abaixo de 1024px, `x = 4.5` / `6.5` acima) e falharam nas duas: a esfera ficava atrás do painel no desktop e atrás do texto no celular. A conta é incompatível — a altura do texto é medida em PIXELS e a viewport em `svh`, então a sobra depende da largura **e** da altura e muda quando uma linha a mais quebra. Não existe constante que sirva de 320px a 2560px: **não reintroduza o posicionamento por faixa de largura.**
- **O posicionamento é medido, e a esfera vai o mais perto do CENTRO DA TELA que o tamanho permitir.** A ordem de prioridade é a do dono — sem sobreposição (restrição dura), depois tamanho, depois centro — e é ela que a implementação segue: `findFreeSpot` dá o maior vão (a régua), `findSpotNearest` dá o ponto mais perto do centro com ≥`centerSizeFloor` (**0,8**) desse raio, e o segundo vale quando existe. **As três exigências não cabem juntas em toda tela**: o meio da tela no desktop é um corredor entre o texto e o painel, medido em ∅455 contra ∅861 de vão em 2529×1344 — centrar **exatamente ali custa ~metade do tamanho**. Por isso a fração é 0,8 e não 0,6, e por isso existe um plano B: a 120px do centro a porteira já admite os 0,8 (∅692), e é esse o ponto que o `findSpotNearest` devolve — o mais perto do centro que o piso alcança. **O piso não desloca a faixa viável, ele decide se ela EXISTE no centro**: a bolsa central é uma porteira entre o canto inferior esquerdo da nav e a borda de cima do `h1`, e em 2529×1344 ela admite no máximo 0,84 do maior vão — com `0,9` a porteira fica fechada e a esfera era empurrada para a direita (57% da largura em 2529×1344, **79% em 2560×1320**, a queixa do dono na tela dele). **Não reintroduza o 0,9 sem ler a nota do `0,8` no `screenBudget.js`**: o ponto mais central que satisfaz `0,9` fica a 0,1–0,3px da fronteira, e a alternativa "gasta tamanho só onde compensa" (câmbio, faixa morta, passo fino) foi medida e descartada — estaca num ombro e devolve a esfera à direita. Depois do vão ainda passa o teto da nuvem (bullet da nuvem): o raio do vão é a régua das ÓRBITAS. As telas acima de 2560px **já foram medidas num modelo de reancoragem** do dump de 2529×1344 (a coluna trava em `max-w-7xl`, então o layout seria o mesmo deslocado) e o modelo estava errado: em 2026-09-23 os viewports até 7680×4320 foram medidos com dumps de verdade (`setDeviceMetricsOverride` na largura da linha) e o 4K saiu em ∅1386 contra os ∅1088 que o modelo previa — ele não via que a coluna travada deixa um vão central enorme. **Meça no navegador, não reancore**; a tabela vai até 7680×4320 no `DESIGN.md`.
- O Hero marca com `data-hero-occupied` o `div` do logo, a nav do desktop, as **5 folhas** do bloco de texto (eyebrow, `h1`, tagline, subline, CTAs) **e o wrapper do painel de calibração** — **folhas, não caixas**: `getBoundingClientRect` inclui o padding, e o `lg:pr-80` do bloco punha 320px de obstáculo além da tinta. **Cinco** dessas folhas (`h1`, tagline, subline, eyebrow, CTAs) levam `data-hero-occupied="ink"`: são `block`/`flex`, então a caixa vai até a borda da coluna — o `h1` mentia 200–280px para a direita e o eyebrow/CTA tinham 896px de caixa com ~300px de tinta, e a caixa mentirosa deles cai justamente na faixa do meio que o centrado procura. O `measure` usa `Range.getBoundingClientRect` **unido às caixas dos filhos** (o `Range` só pega nós de texto, e o eyebrow tem um ponto de acento que é `<div>`). O `ThreeCanvas` mede esses retângulos via `container.parentElement` — o div do canvas é *irmão* do wrapper, não ancestral. O grupo é escalado pela **silhueta**; abaixo de `floorRadiusPx` fica invisível. Detalhes e a tabela medida em `DESIGN.md`.
- **O painel de calibração É obstáculo**, e o wrapper dele leva `data-hero-occupied` (com o `hidden lg:block` nele, para medir 0×0 abaixo de `lg`). O vidro (`.tech-glass`, `z-30`) admitiria a esfera por trás, e houve uma tentativa de liberá-lo — mas atravessá-lo por baixo da moldura lê como defeito, e "sem sobreposição" é a restrição dura. O preço está medido: são ~317px de altura bloqueando a metade direita da faixa central, e é por isso que a esfera não fica no meio no desktop.
- **A escala é a inversão da SILHUETA, não a do polo próximo** — `envelopeWorldRadius` em `src/utils/screenBudget.js`. Medir a projeção no polo próximo (`d − ρ`) deixava a esfera desenhando **63% (desktop) a 72% (mobile)** do vão reservado; corrigido, a **tinta toda** enche o círculo reservado por construção: a nuvem em repouso desenha 100% dele e as órbitas 110%, na envolvente da nuvem (ver o bullet das órbitas). Fora do eixo a projeção vira elipse alongada na direção radial e a tangência é resolvida por bisseção com o `offsetPx` — sem esse termo a esfera vaza o vão em tela larga. `ORBIT_RADIUS = 6.0` é **constante de propósito**: uma referência viva faria as órbitas encolherem ao arrastar o slider de distorção de 0,6 para o topo (0,8) — e encolheriam justamente o que o olho lê como "a esfera".
- **A TINTA tem teto próprio, e ele só morde em tela muito larga** — `radiusWithinGap`, chamado no `adjustLayout` logo depois de escolher o vão. O que ele limita passou a ser a tinta TODA em 2026-09-23: a nuvem no extremo do slider **e** as três órbitas, que são desenhadas na mesma envolvente (`ORBIT_ENVELOPE_RATIO = cloudRatio`). A nuvem cresce com o slider (`5,4 + distortion + 0,4` de mundo = **110% de `ORBIT_RADIUS`** no topo) e a inversão da silhueta é convexa, então +10% de mundo dá **mais** que +10% em tela. Quem absorve esse excesso é a folga de `marginPx`, que é **absoluta** (cresce com a altura) contra um excesso **relativo** (cresce com o raio): os dois se cruzam quando o raio passa de ~35% da altura, o que medido acontece a partir de **~3440px de largura**. Dali para cima, se a nuvem no topo do slider passaria do obstáculo mais próximo, o raio cede o mínimo — medido com dumps reais: 0,1% em 3440×1440, 0,3% em 3840×2160, 2,1% em 5120×1440 e 3,3% em 7680×4320 — e até 2560px **nada muda**. A concessão é conservadora: a conta compara a silhueta na direção radial (o pior caso) enquanto o obstáculo pode estar em outra. **Mas o `obstacle` que ela recebe ignora as bordas do container** (é o `obstacle` do `freeSpot.js`), então a garantia é contra o CONTEÚDO, não contra a moldura do hero: no caminho do plano B — o maior vão, por definição encostado numa borda — a tinta de 110% passa da borda e é cortada pelo `overflow-hidden` da seção, por algumas dezenas de px em tela larga. É corte de um fio de linha num caso que hoje não é alcançado (nenhuma viewport medida cai nele).
- **O teto da guarda é `folga / (cloudRatio − 1)`, e é isso que torna a folga negociável.** O excesso da nuvem sobre o círculo é `(cloudRatio − 1)` do raio, e ele é comparado com uma folga **em pixels**: a conta só fecha — isto é, a guarda só deixa de morder — enquanto `raio ≤ folga / (cloudRatio − 1)`. Com `cloudRatio = 1,1333` (soma 6,8) esse teto era **7,5× a folga**; com `cloudRatio = 1,100` (soma 6,6) ele é **10×**. É por isso que a folga pôde cair de 24 para 16px de respiro sem preço nenhum em tela larga: **o que sustenta a guarda não é a folga em si, é a razão entre a folga e o excesso relativo.** Abaixar o topo do slider é, portanto, a alavanca indireta do tamanho — e foi assim que o círculo cresceu no pedido anterior do dono, sem tocar em uma vírgula do vão (∅666 → ∅692 no monitor dele, com a bola enchendo o círculo). O pedido SEGUINTE, o das órbitas, usou a mesma razão pelo outro lado: `ORBIT_ENVELOPE_RATIO = cloudRatio`, ou seja, os anéis consomem a envolvente que a guarda já reservava para o pior caso da nuvem — por isso a mudança não custou folga nem raio nenhum, e por isso o `cloudRatio` virou o teto dela.
- O `cloudRatio` é o **contrato com o shader** e mora no `ThreeCanvas` (`(CLOUD_BASE_RADIUS + CURSOR_PUSH + SLIDER_MAX_DISTORTION) / ORBIT_RADIUS`) porque os três números são de lá: o `IcosahedronGeometry`, o `interaction *` do vertex shader e o topo do slider "Flux Dynamics". **O que é fixo é a SOMA, não cada parcela** — e foi essa a alavanca que fez a esfera crescer três vezes em 2026-09-23, a pedido do dono ("pode aumentar um pouco o tamanho da esfera", "ainda dá para aumentar um pouco mais", "ainda dá para aumentar um pouco mais a esfera e aumente as órbitas também"): 4,0 + 0,8 + 2,0 → 4,8 + 0,8 + 1,2 (**+17%**) → 5,4 + 0,4 + 1,0 (**+11%**) → **5,4 + 0,4 + 0,8** (**a soma caiu de 6,8 para 6,6**, atual). As três primeiras linhas trocam parcelas dentro da soma e por isso o `cloudRatio` não muda: o `radiusWithinGap` devolve os mesmos números em toda tela e só o repouso cresce — no padrão do slider (0,6) a nuvem desenhava 77% do círculo reservado, depois 90%, depois **100%**. **A quarta é diferente: ela BAIXA a soma**, e portanto baixa o `cloudRatio` (1,1333 → 1,100) — a guarda morde menos em toda tela larga, o teto `folga / (cloudRatio − 1)` sobe de 7,5× para 10× a folga, e é isso que permitiu **cortar a folga** (`BREATHING_PX` 24 → 16 e `PARALLAX_WORLD` 0,5 → 0,4) e ainda assim devolver um círculo maior: no monitor do dono a guarda morde nos mesmos casos de antes, com o mesmo raio reservado, e a bola sai de ∅666 para **∅692**. O preço é o empurrão do vértice sob o cursor (`CURSOR_PUSH`, 0,8 → **0,4**) e o topo do slider (2,0 → 1,0 → **0,8**, com o padrão 0,6 agora a 75% da pista); empurrão e topo são intercambiáveis dentro da soma — **subir o raio-base sem ceder um dos dois é que não dá**, porque aí a guarda encolhe a esfera em 3440/3840/5120. A subdivisão do icosaedro sobe com o raio (20 → 24 → **27**, densidade de pontos constante) e a frequência do ruído cai na mesma proporção (0,8 → 0,667 → **0,593**), para o desenho aprovado não mudar — o ruído é amostrado na posição local. **Em 2026-09-23 ele deixou de ser só o pior caso da nuvem:** é ele que define o raio das órbitas (`ORBIT_ENVELOPE_RATIO = CLOUD_MAX_RATIO`), e é essa igualdade que faz um anel de 1,1 herdar a garantia inteira — um anel de raio de mundo `R` está sobre a casca da esfera de raio `R`, e a imagem da esfera é a região da silhueta que o `radiusWithinGap` já continha. Consequência para quem mexer: o topo do slider move os anéis **direto** (para baixo eles encolhem junto com a envolvente), não só pela folga.
- **O teto de tamanho é `0,42 * altura` e hoje ele NÃO decide em tela nenhuma que foi medida.** A versão anterior deste arquivo dizia que em 5120×1440 ele era quem mandava, com a esfera em 84% da altura; medido com dumps reais em 2026-09-23, a esfera sai em **78%** ali e em **74%** em 7680×4320 — quem manda é o piso do `findSpotNearest` (0,8 do vão), não o teto. E há um motivo estrutural: `ceilingPx = min(spot.radius, capRadiusPx)` e o raio do vão nunca passa de `min(width, height)/2` (o amostrador inclui as bordas), então um ponto que veio da busca centrada tem raio ≤ `0,8 · min/2 ≤ 0,4 · altura` — **abaixo do teto por construção**. Ele só pode morder no caminho do plano B (o `findFreeSpot` cru, que encosta na borda), e continua sendo a rede contra número degenerado: sem ele, num vão enorme, `ρ` se aproxima da distância até a câmera e a tangente de `envelopeWorldRadius` explode com o `gl_PointSize` junto.
- **A folga é derivada, não constante.** `DEFAULT_MARGIN = 32` no `freeSpot.js` é só o padrão de quem chama a função solta; o Hero passa a sua, vinda de `viewportBudget`: **16px de respiro + 8px da animação de entrada** (`animate-fade-in` começa em `translateY(8px)` e a medição roda no mount) **+ a paralaxe da câmera em px** (`PARALLAX_WORLD * fPx / distance` com `fov` de 50°, ~21px num hero de 900px e ~34px num de 1440px), esta última **só onde há ponteiro** (`hasPointer`; sem `mousemove` a câmera não anda, e um telefone de verdade cai nesse caso — a folga dele é 24px, não 39). O respiro era 24px e cedeu a 16 em 2026-09-23 junto com a excursão da câmera (0,5 → 0,4): **os dois só puderam cair porque a quarta parcela da soma da nuvem baixou o `cloudRatio`** (ver o bullet da nuvem, `folga / (cloudRatio − 1)`) — cortar folga com a soma antiga de 6,8 custaria 20% do raio em 3440px. A folga de 8px de paralaxe que existia no papel era 3–5× menor que o real. A mesma folga **não** é usada contra as bordas do container, e a versão anterior deste arquivo registrava o contrário: existia um `edgeMargin` opt-in para isso, e ele saiu do módulo. Quando o maior círculo está encostado numa borda — e no desktop ele está, no topo — exigir 56px das quatro bordas tira **~15% do raio**, e a esfera centrada saía menor que o plano B. Ao **somar um elemento fixo ao Hero, marque-o** com `data-hero-occupied` — um elemento não marcado é um lugar onde a esfera pode cair em cima.
- A medição roda no mount, no `ResizeObserver` do container **e em `document.fonts.ready`** — Inter/JetBrains vêm do Google Fonts e chegam depois, e o texto medido com a fonte de fallback tem outra altura (o `ResizeObserver` não cobre isso: o container é `inset-0` e o hero é `min-h-screen`, então a caixa não muda quando o texto cresce dentro dela).
- **Não há mais desconto de opacidade no mobile.** O `opacity * 0.55` era paliativo para o enxame atrás do texto; com o vão livre não há sobreposição para o `AdditiveBlending` lavar, e o `uOpacity` é a prop direta.

**Estratégia responsiva.** Não existe detecção de viewport em JS: `src/utils/viewport.js`, `useViewportDimensions`, `isMobile` e o `<section>` com altura/largura inline foram **removidos**. O layout é coluna vertical. O `< 1024` do `ThreeCanvas` (que decidia o `pixelRatio` do renderer e o recuo em `z` — e **não** posicionava nada) **saiu de dentro do componente** para `viewportBudget`; onde a esfera fica continua medido, não estimado. Não recrie um hook de viewport — comportamento por breakpoint é classe `md:`/`lg:`.

- **O texto do Hero abaixo de 768px é menor e a barra de nav do mobile não existe mais** (2026-09-23, os dois pedidos do dono: "diminua um pouco as fontes dos textos do hero e coloque as margins-top para 1 rem" e "no mobile, retire a barra de navegação superior"). São dois cortes que vão para o mesmo lugar — espaço para a esfera. O bloco de texto perdeu ~119px de altura em 390×844 e ~145px em 360×667, e a barra levou ~54px (30px de pílula + `mt-5`) da faixa logo abaixo do header. Medido no DOM real, a esfera sai de ∅258 → ∅310 → **∅309** e de ∅96 → ∅219 → **∅262**; em 390×844 o tamanho não muda com a barra porque ali o vão é limitado pela **largura** (∅390, o teto dos 390px) — o ganho aparece na **centralização**, de 123px para **67px** do meio. Os `sm:`/`md:` devolvem o tamanho antigo a partir de 640/768px, então tablet e desktop saem byte a byte iguais, e **acima de `md` a barra não existia** (768×1024 não muda uma vírgula: ∅555/∅443). **O efeito não é o mesmo em todo telefone, e a diferença importa:** 360×667 e 320×568 são limitados pela **altura** (∅219 → ∅262 e ∅109 → **∅152**), 500×714 vai de ∅260 para **∅302**, e 320×480 — o único caso em que a esfera era escondida, abaixo do piso de 48px — passa a aparecer com **∅96**, no piso exato. Ao mexer de novo aqui, meça os quatro.

**Estilo.** Tailwind 3 com tokens reais em `tailwind.config.js` → `theme.extend`: `fontFamily.sans` (Inter) / `mono` (JetBrains Mono), `colors.accent` (`#f97316`) / `surface` / `panel`, `transitionTimingFunction['out-expo']` (`cubic-bezier(0.16, 1, 0.3, 1)`, usada como `ease-out-expo`), e `keyframes`/`animation` de `fade-in` e `flow`. A identidade completa está em **`DESIGN.md`** — leia antes de estilizar qualquer coisa nova.

> **O variant `hover` (e o `group-hover`) foram sobrescritos no `tailwind.config.js`** para exigir ponteiro real: `@media (hover: hover) and (pointer: fine)`. Isso torna todo `hover:` do projeto touch-safe de uma vez, sem `md:hover:` espalhado. Os **dois** variants foram sobrescritos porque `group-hover` é um variant core separado — cobrir só o `hover` deixava as 4 regras de `group-hover` grudando no toque. Se um dia um hover precisar valer em telas de toque, ele **não** vai funcionar por esse caminho: use `active:` ou `focus-visible:`.
>
> O sistema de hover é fechado: **300ms** para superfície/card, **200ms** para botão/ícone, sempre `ease-out-expo`, e **todo** elemento interativo tem `focus-visible:ring-2 ring-accent/70`. Hover de movimento (`-translate-y-*`) e `.card-tilt` **não convivem** no mesmo elemento — os dois escrevem `transform` e o inline vence. Ver "Hover" no `DESIGN.md`.

> O CSS compilado do Tailwind 3 é **plano**: `@layer` aparece **0 vezes** na saída (é construct de compilação, não de runtime). A ordem efetiva é base → components → utilities não-prefixadas → regras custom → utilities responsivas. Logo, uma regra custom vence uma utility não-prefixada, mas **perde** para a responsiva. **Nunca conte com uma classe do `index.css` para sobrepor `md:text-6xl`.**
>
> Pela mesma razão, **`className="px-4"` não sobrepõe um `px-5` interno de um componente** (a cascata é a posição no CSS gerado, não a ordem no `className`). Por isso `Button` expõe `size` e `iconPosition` como props em vez de deixar o chamador passar classes conflitantes. Não há `clsx` nem `tailwind-merge` — decisão consciente; as primitivas concatenam `className`.

## Convenções e armadilhas conhecidas

- **Não há `prop-types`** em lugar nenhum, embora o ecossistema esteja carregado no ESLint. Todo componente com props abre com `/* eslint-disable react/prop-types */`. **Siga a convenção de disable por arquivo** — não introduza `prop-types` nem migre para TypeScript sem que isso seja pedido.
- O `.eslintrc.cjs` fixa `settings.react.version` em `'18.2'` enquanto o React **19** está instalado — defasado, e fonte de regras do `plugin:react/recommended` disparando de forma imprecisa. O `parserOptions` também não define `ecmaFeatures.jsx`.
- **Os labels do painel de calibração vêm do locale** (chaves `calib*`: `calibTitle`, `calibDistortion`, `calibThreads`, `calibClock`, `calibDensity`, `calibEnergy` e `calibColorOrange`/`Blue`/`Green` — estas três só em `aria-label`). Eram **em inglês hardcoded por decisão explícita** ("são readouts de instrumento, não prosa"), e a regra era não traduzir sem falar com o dono; ele pediu a tradução em **2026-09-23** e o painel passou a ler o mesmo objeto `text` do resto do site. O `HeroCalibration` recebe `text` do `Hero` (que já tinha), e o array `SLIDERS` guarda só o que é neutro de idioma (`key`, `min`, `max`, `step`, `showValue`) — o label é passado em cada `RangeControl`. **Ao adicionar um label, adicione nos dois arquivos de locale** (a paridade hoje é 38 chaves em cada um). As três bolinhas de cor são as mesmas do acento/superfície e continuam hardcoded no JSX: só o rótulo acessível é traduzido.
- **Cor do ícone de tech vai na custom property `--brand`**, via `style={{ "--brand": color, "--glow": color }}` no tile, e o ícone usa `group-hover:text-[color:var(--brand)]`. O `--glow` é a mesma cor e alimenta o `.pointer-glow` (sem ele o spotlight do tile sairia no acento, não na cor da marca). Não volte para `style={{ color }}` direto no ícone: era esse o motivo de o `hover:text-black` do portfólio antigo nunca funcionar (a cor inline vencia a classe).
- **Marcas de cor branca** (`#ffffff` em Next.js e Express): o `group-hover:text-[color:var(--brand)]` não produz mudança visível nelas. O feedback vem do `scale-110` + `drop-shadow-[0_0_14px_currentColor]`. Não "conserte" trocando a cor oficial da marca.
- **A lib subiu para `react-icons@5.7.0` em 2026-09-23**, a pedido do dono (`import { SiClaudecode } from "react-icons/si"`): na **5.0.1 não existe glifo nenhum da Anthropic** — nem `SiClaudecode` nem `SiClaude` —, e por isso o tile do Claude usava `TbSparkles` (genérico de IA) na cor oficial `#D97757`. O preço do upgrade foi medido no **runtime** dos dois pacotes (o `index.d.ts` só lista nomes, não prova que o glifo existe): o Simple Icons **removeu `SiAmazonaws` e `SiOpenai`** (e `SiPlaywright`, que já não estava no grid), então dois tiles trocaram de conjunto — **AWS** → `FaAws` (Font Awesome, o mesmo conjunto do React e do Node) e **Codex** → `RiOpenaiFill` (Remix Icon), mantendo a marca dona, mesmo critério que faz o Gemini aparecer com `SiGoogle`. Os outros **17** ícones do grid sobreviveram (conferido um a um). **Não há versão que tenha `SiClaudecode` junto com `SiAmazonaws`/`SiOpenai`** — se um dia o grid precisar de outro ícone que só exista numa versão antiga, o caminho é trocar o conjunto do tile (como aqui), não voltar a lib.
- **O rótulo do tile é "Claude" e o glifo é o do Claude Code** (`SiClaudecode`), que é um desenho **pixelado** e não a estrela do produto — a 5.7.0 também traz `SiClaude` (a marca do produto), e a troca é uma palavra em `techs.js:77`. Foi o que o dono pediu pelo nome; se ele estranhar o desenho, é este o histórico.
- Os labels de tech **são os nomes próprios das marcas** — não vão para o locale (é a mesma exceção dos nomes próprios), e a lista vem inteira de `techs.js`.
- **O Hero depende de empilhamento explícito** (`z-0` glow / `z-[1]` canvas / `z-[2]` `.grid-overlay` / `z-20` conteúdo / `z-30` painel) e de `relative overflow-hidden` no `<section>`. Nunca use z negativo. O grid fica **acima** do canvas — atrás dele a grade de 32px ficava invisível sob o `AdditiveBlending`. Detalhes em `DESIGN.md`.

Se o padding horizontal voltar para o `<section>`, o `max-w-7xl` já vem encolhido 48px e o Hero sai desalinhado de todas as outras seções.

Dois valores **não** mudaram, e pelo mesmo motivo (−2rem é maior que o próprio valor): o `py-6 md:py-12` do Hero (é o gutter dele, e zeraria no celular) e o `pb-8` do rodapé (encostaria o copyright na borda inferior).
